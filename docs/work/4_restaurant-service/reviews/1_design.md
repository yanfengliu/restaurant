## Reports

### Codex independent concrete-contract reviewer

**F1 — Medium: the original recovery guidance recommends a sink for dishes that the approved graph cannot remove from an underfilled rack.** At the reviewed target, `design.md:61` says that additional dishes, legacy sinks or deliveries can resolve the shortage. Consider four live plates, no pending delivery, and a reachable dishwasher. Machine preference (`design.md:29`) commits all four to `rackDirty`. The rack waits for five (`design.md:41`), no dirty-rack extraction task exists, and selling or moving the occupied machine is refused (`design.md:53`). An added sink cannot reach those four units: existing sink job selection accepts ordinary `dirty` ware (`src/engine.js:635-641`), while the new unload task accepts only `rackClean`. Therefore the guidance can send the player to spend money on an appliance that does not recover the loaded dishes. Keep the full-five rule and state the actual recovery: additional dishes that can enter service, or completing deliveries, can supply the missing dirty units; a sink remains an alternative for uncommitted dirty dishes. A new drain action or partial cycle is unnecessary for this correction.

The specified machine ownership is otherwise coherent. Keeping incoming reservations derived from `machine-collect` and `machine-load` avoids a second persisted occupancy counter. Deposit exchanges the incoming claim for one rack record, and clean pickup exchanges that rack claim for one employee-held dish. Those transitions can preserve `incoming + physical rack <= 5` without counting the same unit twice. The five-dirty trigger, five-washing invariant and single `washProgress` rule (`design.md:41-45,55`) exclude accidental mixed active batches and independently timed dishes. Mixed clean/dirty inactive racks are valid while clean dishes leave and new dirty dishes arrive. A clean dish must keep its physical slot until pickup, not merely until completion of the timer.

The cabinet reservation already has an appropriate representation. `reservedStorage` counts every ware record carrying `returnStorageId` (`src/engine.js:137-138`), so keeping that field across incoming, rack and carried-clean states reserves exactly one destination slot throughout. `usedStorage` counts stored clean ware (`src/engine.js:134-135`); storage arrival must remove the return link as it adds the clean storage link, preventing double counting. Dismissal of an unheld collector removes both claims, whereas dismissal of an unloader removes only its assignee. The distinction in `design.md:51` is correct. In particular, a generic extension of `releaseAssignment` must not erase a rack's return reservation: the current helper clears a dirty collector's reservation (`src/engine.js:596-603`), a narrower case than rack unloading.

The route contract handles the difficult transition at clean pickup. Proving the route at assignment and checking it again immediately before taking the unit (`design.md:43`) prevents a worker from acquiring an avoidably stranded clean dish after a cabinet move or route closure. If the return route is no longer possible, leaving the unit and its reservation on the rack while releasing only the unload assignee is internally consistent. After pickup, an ordinary blocked carrying task may retain the dish until access returns. This matches the existing explicit blocked-task representation (`src/engine.js:588-593`) and validation of an actually unreachable target (`src/engine.js:1209-1214`). A future cabinet move remains permissible before it is the active return target; deletion remains prohibited by the reservation (`src/engine.js:835`). No second path system or speculative automatic rerouting service is needed.

The existing cleanup and validation helpers need complete, narrow extensions, rather than a redesign. `resetStaff` and `setWare` currently remove only known legacy fields (`src/engine.js:477-483`), and current ware validation requires a reciprocal employee for carried/washing states (`src/engine.js:1248-1251`). The contract's exact permitted links require new machine and rack fields to be removed at every corresponding transition, including breakage and rejected pickup. Autonomous rack records must have no `staffId`, while an optional `assigneeId` on a clean rack must have exactly one reciprocal unload task. The single per-dish reservation and ledger rules continue to apply. These are implementation acceptance points already required by the approved graph, not new persistent schema requirements.

The wage contract retains the sound mechanism from round 0. Existing code accepts accrued debt up to a monthly salary plus tolerance at every day phase (`src/engine.js:1203`), accrues by elapsed simulation time (`src/engine.js:757-764`) and pays the outstanding amount on dismissal (`src/engine.js:865`). Carrying that debt through load and paying it once at the next daily boundary preserves accepted historical money. For salary M and day phase p, the proposed ceiling M + Mp/450 grows at exactly the same rate as the liability until settlement, then the reset debt fits the reset phase. Test both old accepted maxima and new phase-aware maxima through advancement and reload; a test only loading typical month-to-date debt would miss the forward-validity edge. Existing day-reset bookkeeping at `src/engine.js:770` supports the declared choice to attribute the boundary payment to the new day's expenses. Version 1's zero-accrual conversion (`src/engine.js:1271`) remains the correct already-paid treatment.

Round 0's F0 is repaired in `design.md:29`: sinks remain purchasable and the existing Chef's Tasting Plate dependency remains available. Adding the dedicated dishwasher while keeping legacy sink tasks avoids destructive conversion and preserves historical work. It also honestly means that the browser can still use sinks where the studied native sink's role is unknown. Research at `docs/research.md:227-229` distinguishes the observed five-dish unattended cycle from the unobserved duration and clean pickup. The explicit four-second employee-retrieval fallback is therefore a bounded authored choice, not an unsupported native-match claim. Continuing implementation does not require another unbounded native study or a general appliance scheduler.

Two nonblocking implementation interpretations were communicated to and accepted by the coordinator. First, API `progress` is raw `object.washProgress / 4`, while `remainingSeconds` is `4 - object.washProgress` during the cycle; at raw progress 3 seconds, those values must be 0.75 and 1. The phrase “four minus that progress” in `design.md:59` must not be implemented as four minus the normalized fraction. Second, fewer than five global live plus prepaid units proves a shortage, but a total of five or more does not prove that a particular rack can fill. Units can be elsewhere, unavailable through routes, or of a tableware type the current menu never dirties; the catalog exposes six tableware types while current recipes use plates and bowls (`src/catalog.js:37-52`). Keep the per-rack “needs more dirty dishes” status truthful and do not convert the global count into a guarantee of availability. These observations do not require another persisted counter, a partial cycle or broader recipe work.

The contract supplies sufficient state, compatibility and conservation boundaries for the engine and interface workers to proceed. Exact transition ordering, field cleanup, all accepted-save bounds and end-to-end service still need implementation evidence. This round finds no other material contract flaw and does not approve code that has not been inspected.
